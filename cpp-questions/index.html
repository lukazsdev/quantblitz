15 C++ questions quant dev interviews actually ask

Quant developer interviews are not LeetCode. They test whether you know what the machine does with your code. These are real questions from the quant blitz C++ track, with the answer and the reason. C++20, GCC or Clang, x86-64.

1Move semantics

Why is moving a std::array<std::string, 1000> far more expensive than moving a std::vector<std::string> of 1000 strings?

Answer

std::array stores its strings inline, so each must be moved.

std::array is a fixed-size aggregate with its elements inside the object, so its move constructor moves every element, O(n). std::vector owns a heap buffer, and its move just steals the pointer, O(1). Large arrays also make objects big, which matters for anything that moves them around.

2RAII

What happens by default if an exception escapes a destructor?

Answer

std::terminate is called: destructors are noexcept by default.

Since C++11, destructors are implicitly noexcept, so an exception leaving one calls std::terminate and the program aborts. Even with noexcept(false), throwing during stack unwinding from another exception terminates. Destructors should swallow or log errors instead of throwing.

3Smart pointers

What advantage does std::make_shared<T>(...) have over std::shared_ptr<T>(new T(...))?

Answer

It allocates the object and its control block together, in one go.

std::shared_ptr needs a control block for its reference counts. std::make_shared allocates that block and the object together, saving an allocation and keeping them adjacent in memory. One caveat: the combined block is only freed when the last weak_ptr is gone too.

Two threads each hold their own shared_ptr copy pointing at the same object. What is thread-safe?

Answer

Copying and destroying their copies, but not the object itself.

The control block's reference counts are updated atomically, so separate shared_ptr instances can be copied and destroyed in different threads. Concurrent reads of the pointed-to object are fine, but writes to it need synchronization, and so does a single shared_ptr instance that one thread modifies while another uses it (C++20 adds std::atomic<std::shared_ptr<T>> for that). shared_ptr makes ownership thread-safe, not the data.

4Special member functions

A base class declares virtual ~Base() = default; and nothing else. What happens to its move operations?

Answer

They aren't declared, so moving a Base silently copies instead.

Any user-declared destructor, even = default, suppresses the implicit move constructor and move assignment. Copies still work, so rvalues fall back to copying with no error. Polymorphic bases that should be movable must declare all five: Base(Base&&) = default; and friends.

5Caches

Roughly how much slower is a load from main memory than a load that hits the L1 cache?

Answer

About 100 times (roughly 100 ns vs 1 ns).

An L1 hit takes 4 or 5 cycles, 1 to 2 ns. On current x86-64 servers, L2 hits cost about 4 to 5 ns, L3 hits roughly 15 to 35 ns and DRAM accesses 100 to 130 ns. That gap is why cache misses, not arithmetic, dominate so much real-world performance.

Why are open-addressing ("flat") hash tables often faster than std::unordered_map?

Answer

Entries sit inline in one array, so lookups avoid pointer chasing.

The standard requires unordered_map to keep element addresses stable, which practically forces a separately allocated node per element plus a bucket array of pointers. Flat tables, like absl::flat_hash_map or boost::unordered_flat_map, probe a contiguous array instead. Fewer allocations and cache misses usually make them several times faster.

A loop follows a random chain of pointers through an array. Why does each step get dramatically slower as the array grows from kilobytes to gigabytes?

Answer

Every dependent load now misses the caches and waits on DRAM.

While the chain fits in L1 or L2, each hop takes 1 to 5 ns, L3 hits take roughly 15 to 35 ns, and beyond the last-level cache every hop waits 100 ns or more for DRAM. Because each address depends on the previous load, the CPU can't run hops in parallel to hide the latency. That's why graph and tree traversals over large data are so latency-bound.

6Branch prediction

Roughly what does a branch misprediction cost on a modern x86-64 core?

Answer

About 15 to 20 cycles of wasted pipeline work.

On a misprediction, the CPU discards the instructions it executed speculatively and restarts from the correct target, which wastes roughly the length of the pipeline. At billions of cycles per second that's only a few nanoseconds, but in a hot loop with unpredictable branches it can dominate. That's why sorted data or branchless code can be many times faster.

Why can a virtual call inside a hot loop over objects of many different types be slow?

Answer

Its target changes unpredictably, so the indirect call mispredicts.

An indirect branch's target is predicted from history like any other branch, so a call site that always hits the same type is cheap. When object types alternate randomly, the predicted target is often wrong. Sorting objects by type, or keeping one container per type, makes the targets predictable.

7Allocation

Why can a single new occasionally take microseconds instead of nanoseconds?

Answer

The allocator sometimes asks the OS for memory, then page-faults it in.

Most allocations are served from free lists in user space and take tens of nanoseconds. Occasionally the allocator has to request memory from the kernel, which involves a system call, and touching those fresh pages costs a fault per page. These rare events create the latency spikes that hot paths must avoid.

8Atomics and memory ordering

What does a release store paired with an acquire load that reads its value guarantee?

Answer

All writes made before the release are visible after the acquire.

Release/acquire creates a happens-before edge between exactly those two threads: everything before the release store is visible after the acquire load that observes it. It doesn't impose a global order on unrelated atomics; that's what seq_cst adds. Mutex unlock and lock use the same release/acquire semantics.

9Lock-free queues

Why do fast SPSC queues put head and tail on separate cache lines?

Answer

Otherwise each index update invalidates the other core's copy.

Cache coherence works on whole cache lines, so two variables written by different cores on the same line keep stealing the line from each other. Aligning each index with alignas(64) (or std::hardware_destructive_interference_size) removes that contention. Implementations often also cache the other side's index locally to touch the shared line less often.

Why can't a lock-free pop simply delete the node it removed?

Answer

Another thread may have read the same pointer and still be using it.

Between loading top and attempting its CAS, a thread dereferences the node to read next, and another thread may pop and free that node in the meantime. Freeing immediately turns that read into a use after free. Safe reclamation schemes, such as hazard pointers, epochs, reference counting or RCU, delay the free until no thread can still hold the pointer.

10Mutexes

Why is calling a user-supplied callback while holding a mutex risky?

Answer

It may take the same mutex, or others in a conflicting order: deadlock.

Code you don't control can do anything, including calling back into your class and relocking the same mutex, or acquiring locks in an order that conflicts with yours. It also holds your lock for as long as the callback takes. Copy what you need under the lock, unlock, and then call the callback.

11Two more to check yourself

In C++20, what is -8 >> 1?

Answer

-4: since C++20, >> on a negative value is an arithmetic shift.

C++20 requires two's complement and defines >> on negative values as an arithmetic shift, so -8 >> 1 is -4 (it rounds toward negative infinity). Before C++20 it was implementation-defined, and left-shifting a negative value was undefined. Shifting by the type's width or more is still undefined.

sq is a constexpr function. Inside main, is int r = sq(5); guaranteed to be computed at compile time?

Answer

No: a local int initializer doesn't need a constant.

constexpr means a function can be evaluated at compile time; a local int initializer doesn't need a constant, so the call may happen at run time. Clang at -O0 emits a real call here, while at -O2 it folds the result to 25. Write constexpr int r = sq(5);, or make sq consteval, when compile-time evaluation must be guaranteed.
